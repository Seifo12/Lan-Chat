### Recreate flake, root cause

The recreate test failed about one full-suite run in three and reported only
`timed out waiting: secured group created`. Two separate defects, both fixed:

1. The wait conflated "callback fired with null" (a declined creation) with
   "callback never fired". `createSecuredGroup` returns null when the pairwise
   manager is absent, and `recreating a non-legacy group refuses` relies on
   exactly that. The wait now polls for the callback and asserts the value
   separately.
2. The real cause. `createSecuredGroup` was a suspend function that switched to
   `Dispatchers.IO` on entry, overriding the caller. The ViewModel's injected
   test dispatcher was therefore discarded one call deeper. A full-suite run
   leaves about 120 threads parked forever in `UdpDiscoveryManager.startReceiver`
   (one per test class, each on a `DatagramSocket.receive` that job cancellation
   cannot interrupt) plus a `TcpMessagingManager.startServer` accept loop, 188
   live threads in total, so the action queued behind all of them.

`UdpDiscoveryManager.stop()` would clear those threads: it cancels the jobs *and*
closes the socket, and closing is what unblocks `receive()`. Nothing calls it,
because every test class builds a real `LanChatApplication` which starts
networking in `onCreate`, and no test tears it down.

The earlier claim in that test file that the suite runs with "hundreds of leaked
threads from other test classes" was wrong about the mechanism. Only two tests
create raw threads. The hundred-plus leaked threads were `Dispatchers.IO`
workers parked in the managers' receive loops.

## Follow-ups

Not started. Each needs its own decision; none is a 1.8 task.

- **Explicit `protocolVersion` in the beacon and handshake.** The peer protocol
  version is read from `ContactEntity.appVersionCode`, which is really "the app
  version that last introduced that peer", so it drifts whenever a peer is
  upgraded by a path that does not rewrite the contact row. Carry the protocol
  version in `IdentityCard` and the beacon instead. Touches `IdentityCard`,
  `IdentityCardCodec`, the beacon and handshake parsers, and `GroupFanout`'s
  version gate.
- **A dedicated bounded network dispatcher.** `TcpMessagingManager` parks its
  accept loop and up to 25 connection handlers on `Dispatchers.IO`, blocking a
  thread for the whole 30 s socket read timeout each. `Dispatchers.IO` is
  elastic, so this does not deadlock; the cost is thread proliferation and the
  coupling of long-lived idle sockets to unrelated IO and database work, which
  is exactly what made this flake look like a mystery. A bounded pool must be
  sized above the 25-connection ceiling or it deadlocks itself. Proposal only,
  not approved and not implemented.
- **Stop networking in tests.** Every test class leaks a UDP receiver and a TCP
  accept loop because nothing calls `UdpDiscoveryManager.stop()` or
  `TcpMessagingManager.stop()`. Worth fixing so the suite stops paying ~120
  threads for the privilege of running it.
- **`sendMembershipUpdate` and `sendGroupInviteMessage` still hardcode
  `Dispatchers.IO`.** Neither is on the failing path today. They are the next
  candidates if a test needs them off the shared pool. `sendMembershipUpdate`
  also still has no caller at all.
