# Phase 1.8 — Signed group invitations and membership

Status: **spec, awaiting approval. No 1.8 code exists.**

Audit finding: C8. Design basis: `docs/DECISIONS.md` A5 (invitation contents, signed
versioned member list, no auto-create, no free join). Transport approach: A —
the invitation travels as the content of an ordinary signed per-recipient
message, so the 1.3 signature, counter, replay window and version gate apply
unchanged. No new signature algorithm, no new signature domain.

## 0. What this session already changed underneath this spec

Two receive-path bugs were found while scoping 1.8 and fixed first, because the
spec's guarantees would not mean anything on top of them. Both are committed on
`phase/1-security` with failing tests written before the fix.

- **Mesh text inserted on signature mismatch** (`b3372f5`). `NearbyMeshManager`
  logged "Security Alert: Signature mismatch" and inserted anyway, and the check
  verified the text alone while the sender signs the whole 1.3 field set. Now
  `MeshTextReceiver` runs the same `InboundMessageVerifier` over the same field
  set, and only `Accepted` reaches the database. Proven by
  `MeshGroupTextVerificationTest` (6 cases).
- **TCP replay pre-check refused every first delivery** (`807499f`). The text
  branch called `replayGuard.tryAccept` (a write) before verifying, so the
  verifier always saw the id as already seen and returned `Duplicate`. Every
  inbound TCP text since `4ebda5f` was dropped silently. The pre-check is a pure
  `wasRecorded` read now; recording happens only in the accepted branch. Proven
  by `TcpDirectTextReceiveTest` (3 cases, driving `processReceivedPacket`).
- **README corrected** (`96fa25e`): voice was never signature-verified on any
  transport. Only text is enforced, on TCP and mesh.

What is still open and belongs to 1.8 or later: voice/photo/video/file carry no
verifiable signature on any transport; `GroupAnnouncePacket` is unsigned and
still trusted on the mesh and UDP paths (removed by this spec); group fan-out
still goes to every online contact rather than to members (changed by this
spec).

## 1. Locked decisions

These were decided during scoping and are not revisited by this spec.

1. **Scope is full.** 1.8 signs invitations, stores membership, drops non-member
   messages, and refuses to auto-create unknown groups. It also deletes group
   creation and overwrite from the UDP path and removes the mesh
   `GroupAnnouncePacket` branch, because a membership table that an
   unauthenticated broadcast can still write is not a membership guarantee.
2. **Joining requires an explicit accept tap.** A verified invitation creates a
   pending row, never a membership. Auto-join would let a queued or replayed
   invitation enrol a device by itself.
3. **Existing groups become legacy, read-only, never deleted.** Every group row
   present at upgrade time is unattributable (no member list, and `createdBy`
   holds a display name, not a device id). History stays readable; sending is
   refused with an explanation and a "recreate as secured group" action.
4. **Only the creator signs the member list; members may leave on their own.**
   Add and remove take a new list signed by the creator at a strictly higher
   version. Leaving needs no signature, because removing yourself grants nobody
   anything. There is no creator-role transfer; a lost creator device means the
   group can no longer change, only be recreated.
5. **Protocol `CURRENT = 3`, `MINIMUM = 2`.** Old peers keep chatting. Anything
   that needs version 3 (invitations, v3 group messages) is refused toward a v2
   peer with the existing update-needed notice instead of being sent.

## 2. Wire format

### 2.1 New packet type

`PacketType.GROUP_INVITE` with a `GroupInvitePacket` carrying the standard
signed-message fields (`messageId`, `senderId`, `senderName`, `recipientId`,
`timestamp`, `counter`, `protocolVersion = 3`, `signatureBase64`) plus one
content field: `inviteJson`, a canonical JSON string defined below. Like every
signed message it is sent per recipient, because `recipientId` is in the signed
set. Unknown to v2 clients, which drop it silently — hence decision 5: the
sender never sends it to a v2 peer.

Membership updates reuse this packet type with a higher `memberListVersion`.
No second packet type is introduced.

### 2.2 Invitation content

Canonical JSON, fixed field order, `,` and `:` separators with no whitespace,
UTF-8, lexicographically sorted member entries. The sender emits exactly this
shape; the receiver never re-serialises (condition 2).

```json
{
  "creatorId": "<device id>",
  "groupId": "<g_ + 32 lowercase hex chars, 128 bits from SecureRandom>",
  "groupName": "<max 200 chars>",
  "description": "<max 1000 chars, may be empty>",
  "members": [{"id": "<device id>", "pk": "<base64 public key>", "name": "<display, untrusted>"}],
  "memberListVersion": 1,
  "nonce": "<32 lowercase hex chars, 128 bits from SecureRandom>",
  "expiry": 1730000000000
}
```

The signature commits to `SHA-256("LanChat-group-invite-v1" || 0x00 ||
inviteJson bytes as arrived)` as the `contentDigestHex` of the standard
`MessageSigningPayload.Fields` (condition 1). Ordinary text can never parse as
an invitation because it never hashes under that label, and the receiver hashes
the arrival bytes before parsing them, so what is verified and what is read
are the same bytes by construction.

`groupId` and `nonce` are 128 bits from `SecureRandom`, hex-encoded, never
time-based: the current `group_<millis>_<deviceId4>` format is guessable and
dies with this phase (condition 4, first half). `memberListVersion` starts at
1 and strictly increases. `expiry` is a wall-clock millis timestamp; clocks in
this mesh already skew, so receivers allow a small tolerance defined in
section 4 (15 minutes) and never treat a missing or unparseable expiry as
"never expires" — it is a refusal.

### 2.3 Group messages under version 3

Today `groupId` travels in the packet but outside the signed set, so a signed
message can be moved between groups. From this phase, the content digest of
every group text message commits to the group: `contentDigestHex =
digestHex("LanChat-group-msg-v1" || 0x00 || groupId || 0x00 || text bytes)`
(condition 4, second half). Direct (non-group) messages keep the v2 digest
unchanged. A v3 group message sent to a v2 peer is refused before sending with
the update-needed notice, exactly like an invitation (decision 5).

## 3. Tables (migration 13 to 14)

- `groups` gains `creatorDeviceId TEXT`, `memberListVersion INTEGER NOT NULL
  DEFAULT 0`, `isLegacy INTEGER NOT NULL DEFAULT 0`. The migration backfills
  `isLegacy = 1` for every existing row: unattributable history, readable,
  never writable.
- `group_members(groupId, deviceId, publicKeyBase64, displayName,
  addedAt, PRIMARY KEY(groupId, deviceId))`, index on `deviceId`. No foreign
  keys, matching the rest of the schema: deleting a group row must not cascade
  into anything security-relevant, and membership reads stay local to one
  table.
- `group_invites(groupId, creatorId, groupName, memberListVersion, nonce,
  expiry, rawBytes, state, receivedAt, PRIMARY KEY(groupId, nonce))`.
  `rawBytes` is the exact arrival bytes of `inviteJson`, kept so a later audit
  re-verifies what was actually received rather than a re-serialisation.
  `state` is one of `PENDING`, `ACCEPTED`, `DECLINED`, `EXPIRED`, `SUPERSEDED`.
- Invitation nonces reuse the durable replay record: `ReplayGuard.tryAccept(
  creatorId, "invite:" + nonce)` with the same 30-day retention, instead of a
  fourth record-keeping mechanism. A nonce seen inside the window is refused;
  the namespace prefix keeps invitation nonces disjoint from message ids.

`MessageStatusSchemaTest`'s per-version table map gains the 13-to-14 entry,
and every test holding an explicit migration list gains `MIGRATION_13_14`, per
the standing rule.

## 4. Verification order (receive path)

For a `GROUP_INVITE`, in order, each a refusal with a log line and no state
change except where noted:

1. `protocolVersion` is 3, else unsupported (existing verdict).
2. Sender has a contact row with a pinned key; the sender's presenting key
   equals the pin. A key-changed creator is refused here: an invitation from a
   changed identity is exactly what the 1.6 block exists to stop (condition 3,
   first half).
3. Standard `InboundMessageVerifier` over the arrival bytes (signature,
   counter, replay window). Missing signature, bad signature, duplicate and
   too-old are refused as today.
4. `creatorId` equals the pin-verified `senderId`. A packet signed by A naming
   B as creator is refused (condition 3, second half).
5. Membership versus update, decided by local state, not by the packet. If no
   member row exists for `groupId`, this is an initial invitation and the local
   device id must be listed in `members`; otherwise it is refused, not parked
   (condition 3, third half). If a member row exists, this is a membership
   update and absence from the new list means removal: the device transitions
   to `LEFT` per section 6 after every other check passes. Without this split,
   the update that removes a device would be refused for not listing it, and
   removal could never be delivered.
6. `expiry` parses and is within tolerance (now minus 15 minutes <= expiry).
   Unparseable or missing expiry is refused, never treated as forever.
7. `(creatorId, nonce)` is unused via the replay guard; then it is recorded,
   whether the user later accepts or not. Recording on sight, not on accept,
   so a replayed invitation cannot be re-presented after a decline.
8. `memberListVersion` handling. Version is enforced relative to what this
   device has already seen, because a device invited at version 3 has no earlier
   version to compare against and must not be refused for being new. If a member
   row or a non-terminal invite row exists for `groupId`, require a strictly
   higher version; otherwise accept any version greater than or equal to 1. A
   fresh invitation with an unused nonce after a terminal state (`DECLINED`,
   `EXPIRED`) is a re-invite and returns to `PENDING`; the nonce rule (step 7)
   is what stops the old invitation itself from being replayed. A version equal
   to or lower than what was seen is refused.

Only after all eight does the row become `PENDING` and the user get an
accept/decline prompt. Accept writes the member table and flips the invite to
`ACCEPTED`; decline flips it to `DECLINED`; expiry flips `PENDING` to
`EXPIRED` on next open. All three are terminal except `SUPERSEDED`, which a
higher-version update writes over any non-terminal state.

## 5. State machine

| State | How it is entered | Send | Receive group messages | Reads member table |
|---|---|---|---|---|
| No row | — | n/a | dropped, nothing stored, no receipts | — |
| `PENDING` | verified invite, user undecided | refused (no group yet) | **dropped, no receipts** (condition 6): no delivered/read ack, so a pending device leaks no presence | invite row only |
| `MEMBER` | explicit accept tap | fan-out to members (section 7) | accepted iff sender is a current member | yes |
| `LEFT` | self-leave, or an update no longer lists this device | refused | dropped (not a member) | no |
| `DECLINED` / `EXPIRED` | user decline / expiry passes | refused | dropped (not a member) | no |
| `LEGACY` | any group row present before migration 13→14 | refused with explanation + recreate action (condition 9) | shown as history only; new arrivals to a legacy id are dropped, never appended | no |

Transitions: `PENDING → MEMBER` (accept tap only), `PENDING → DECLINED`
(decline tap), `PENDING → EXPIRED` (time), `MEMBER → LEFT` (self-leave, or a
creator-signed update that drops this device), `DECLINED`/`EXPIRED` →
`PENDING` (fresh re-invite with an unused nonce only, section 4 step 8),
any non-terminal → `SUPERSEDED` (higher-version creator update). `LEGACY` has no outgoing
transition except recreation, which creates a *new* group with a fresh random
id rather than converting the row. Nothing transitions automatically on
receipt; every membership change on this device traces to a tap or to a
creator-signed higher version.

## 6. Membership updates and leaving

A higher-version list from the creator arrives as a `GROUP_INVITE` with the
same `groupId` and passes the same eight checks, except step 8 expects a
strictly higher version and no accept tap is required: the member table is
replaced wholesale and the invite row is marked `SUPERSEDED`. Added devices
receive their own invitation separately and still accept explicitly; removal
takes effect for the remaining devices on receipt. A device that finds itself
absent from the new list transitions to `LEFT` and stops sending and
receiving for that group.

Self-leave is local only: delete this device's membership rows for the group
and transition to `LEFT`. No packet, no signature, no counter — it cannot
grant anyone anything, so there is nothing to authenticate. Rejoining takes a
fresh invitation.

## 7. Fan-out (send path)

Recipients for a group send are the current member table intersected with
routable reality: members who are contacts, online, and not key-changed.
Each leg is signed per recipient as today. Skipped members are reported to the
sender per message (key-changed members reuse the existing key-change notice
path), never silently dropped from the user's view.

Concretely excluded: non-contact members (no route exists until paired — see
section 8), offline members (existing fan-out timeout behaviour), and
key-changed members (condition 8: sending to a changed key would undo the 1.6
block for the most sensitive case, a group the user reads as trusted).
Legacy groups refuse the send with the recreate action instead of fanning out
to all contacts, which is what the old code did.

## 8. Members who are not contacts (condition 5)

The invitation carries every member's public key. For members who are not
contacts on this device, the key is stored in `group_members` as a
**group-only, unverified, creator-vouched** key. Exactly what that allows:

- It verifies inbound group messages that claim that member as sender, inside
  that group only.
- It does nothing else. It does not create a contact, does not enable direct
  messages, does not appear in the contact list, and is never consulted by the
  1.6 pin logic.

If a vouched key differs from an existing contact pin for the same device id,
the pin wins outright: the vouched key is ignored, the member is treated as
key-changed for fan-out (skipped) and their messages fail verification against
the pin. A contact the user pinned is never downgraded to a vouched key, and
a vouched key is never promoted into a pin — promotion happens only through
pairing plus explicit user action, as before. The member list UI marks
non-contact members as unverified and not paired; pairing one is the existing
contact flow, unchanged.

The creator is exempt from vouching: the creator's key must equal the pin
(section 4, step 2), no exceptions.

## 9. Paths being closed (condition 7)

- The `GroupAnnouncePacket` branch in `UdpDiscoveryManager` is deleted, and
  the dead `broadcastGroupAnnounce` sender goes with it. UDP returns to
  discovery only. No group row is ever created or overwritten from broadcast
  again.
- The `GroupAnnouncePacket` branch in `NearbyMeshManager` is deleted.
  `GroupAnnouncePacket` stays in the `PacketType` enum (old peers still send
  it) and stays unhandled on TCP (`else -> {}`), i.e. dropped.
- The TCP auto-create blocks (`getGroupById == null → insert`) are deleted for
  every media path. An unknown `groupId` on any transport is dropped, never
  stored, with no receipts (a receipt would confirm the group exists here).
- `createdBy` stops being written from packets. New groups record
  `creatorDeviceId` from the verified invitation; legacy rows keep their
  display-name string untouched as history.

Product change, stated plainly: groups are no longer visible to nearby devices
without an invitation. Discovery shows people, never groups. A user who could
see a group in discovery before 1.8 will not see it after, until someone
invites them.

## 10. Protocol versions (condition 10)

`ProtocolVersion.CURRENT = 3`, `MINIMUM = 2`. The invite packet and v3 group
messages carry `protocolVersion = 3`. Sending either to a peer known to be v2
is refused before sending with the existing update-needed notice; "known"
means the last-seen version from beacons and handshakes, and unknown means
ask-or-wait rather than send-and-hope, because a v2 client drops the new type
silently. Direct text keeps the v2 digest and keeps flowing to v2 peers
unchanged. The implementation must confirm the exact source of last-seen peer
version against the beacon/handshake code; if no reliable source exists, the
conservative rule is refuse-until-known, stated to the user as such.

## 11. Test list

Pure/state-machine tests (no transport):

1. `GroupInviteRoundTripTest` — build, serialise through `fromJson`, verify:
   accepts.
2. `GroupInviteTamperTest` — flip one member key byte, rename the group,
   swap the groupId, drop a member: each refuses.
3. `GroupInviteLabelTest` — the same bytes hashed without the
   `LanChat-group-invite-v1` label do not verify; ordinary text content never
   parses as an invitation.
4. `GroupInviteArrivalBytesTest` — verify-then-parse uses the arrival bytes;
   re-serialised-but-equal JSON with different whitespace still verifies only
   if byte-identical, and parses to the same fields.
5. `GroupInviteExpiryTest` — expired refuses; missing/unparseable expiry
   refuses; inside tolerance accepts.
6. `GroupInviteNonceReuseTest` — same (creator, nonce) twice: second refuses,
   via the namespaced replay guard.
7. `GroupInviteCreatorPinTest` — creator key differing from the pin refuses;
   key-changed creator refuses; `creatorId != senderId` refuses.
8. `GroupInviteSelfMembershipTest` — invitation not listing this device
   refuses without creating any row.
9. `GroupInviteVersionTest` — a version equal to or lower than the seen version
   refuses; a higher version updates; a first invitation at any version 1 or
   above (for example, joining an established group at version 3) is accepted
   to `PENDING`, because version monotonicity is relative to what the recipient
   has seen, not absolute.
10. `GroupTrustStateTest` — the section-5 table as transitions: every allowed
    transition and a refusal for each forbidden one (notably nothing receipted
    while `PENDING`, nothing auto-accepted on receipt).

Transport and storage tests (Robolectric, real database):

11. `GroupNonMemberDropTest` — signed message from a non-member to a known
    group: dropped, nothing stored, no receipts.
12. `GroupUnknownIdNoCreateTest` — message and invite for an unknown groupId
    create no group row and no message row, on TCP and mesh.
13. `GroupPendingNoReceiptTest` — message arriving while `PENDING`: dropped
    and no ack is emitted (assert on the ack seam, as
    `MeshGroupTextVerificationTest` does for the insert).
14. `GroupFanoutMembersOnlyTest` — an online contact who is not a member
    receives nothing.
15. `GroupFanoutSkipsKeyChangedTest` — a key-changed member is skipped and the
    sender is told why.
16. `GroupIdBindingTest` — a v3 group message moved to a different groupId
    fails verification (round-trip style, mirroring
    `SignedMessageRoundTripTest`).
17. `GroupVouchedKeyTest` — non-contact member's message verifies against the
    vouched key; nothing creates a contact; direct messaging stays refused.
18. `GroupPinBeatsVouchTest` — vouched key differing from the pin is ignored,
    member treated as key-changed both directions.
19. `GroupUpdateAndLeaveTest` — higher-version creator update replaces the
    table; removal takes effect; self-leave needs no packet and stops both
    directions; rejoin needs a fresh invite.
20. `UdpGroupAnnounceGoneTest` — a `GroupAnnouncePacket` over UDP creates and
    overwrites nothing.
21. `MeshGroupAnnounceGoneTest` — same over mesh.
22. `GroupProtocolGateTest` — invite and v3 group message to a v2 peer are
    blocked before sending with the update notice; v3 peer flows.
23. `GroupMigration13To14Test` (`MigrationTestHelper`) — legacy rows arrive
    read-only with history intact, pins and key-change flags survive, new
    tables exist with the specified keys.
24. `GroupLegacyRecreateTest` — the recreate action mints a fresh 128-bit id
    and never converts the legacy row.

## 12. Non-goals

- QR-join for non-contacts (deferred already by A5; the invitation carries
  everything a QR would need, so it stays easy later).
- Creator-role transfer; a lost creator device ends the group's evolution.
- Voice/photo/video/file signature enforcement beyond what 1.9 owns; this spec
  changes only the group-text digest.
- mTLS (1.10) and the HPKE layer (1.11); invitations ride the existing
  pairwise encryption unchanged.

  Resolved during implementation: the source is `ContactEntity.appVersionCode`,

  `TcpMessagingManager` beacon handling), and this build advertises
  `UserPreferences.appVersionCode = 3`. A contact never seen advertises

- Whether `senderName` stays in the invite packet at all: it is display-only
  and untrusted either way; keeping it avoids a second UI lookup, dropping it
  shrinks the packet. Recommendation: keep, marked untrusted in code.
