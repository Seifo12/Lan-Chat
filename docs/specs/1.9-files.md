# 1.9 File Transfer Admission

Spec for the inbound file, photo, video, voice and APK transfer gate. Branch
`phase/1-security`. Audit finding C7, decision A6 in `docs/DECISIONS.md`, plus
three holes found in the same gate while scoping it.

Rule: after every task, update `docs/specs/1.9-progress.md`. After a context
compaction, re-read this file, that file, and `AGENTS.md` before touching
code.

## 0. Why this is not just a size limit

Today `handleIncomingFileStream` (`TcpMessagingManager.kt:388`) parses the
stream meta and admits the transfer if a pairwise stream key exists
(`:439`). Three consequences, all fixed here:

1. Any device can make the app accept up to 5 GB across 25 concurrent
   connections, with no consent and no free-space check.
2. The admitted `senderId` is an unauthenticated meta field. It is never
   checked against `pinnedPublicKey` or `hasKeyChanged`, so a key-changed
   peer whose session key still works pushes files straight past the 1.6
   block that texts cannot pass.
3. The APK pull (`TcpMessagingManager.kt:892`) streams the whole APK to any
   device that opens TCP and sends a request, with no contact check, no
   consent and no integrity check. This is larger than the push that A6
   mentions, because it needs no user action at all.

A6 already settles the policy shape: for saved contacts, photos and voice up
to about 20 MB auto-accept, anything larger needs an explicit tap, with
per-peer concurrency, a free-space check, a 2 GB ceiling instead of 5 GB, a
per-peer rate limit, and direct APK push restricted to contacts plus a
confirmation. This spec implements A6 and closes 1 to 3 above, as one policy.

## 1. Scope

In: TCP file stream, mesh FILE payload, mesh inline photo and voice, the APK
pull, the APK push (`recipientId = "any"`), and the consent UI.

Out, deliberately, and not deferred to nowhere: QR join, creator-role
transfer, transport encryption (that is 1.10 mTLS), HPKE, and chunked or
streaming Nearby payloads.

## 2. Constants

One object, one file, `TransferAdmissionLimits.kt`. Every value below has a
boundary test at limit-1, limit, and limit+1, because a limit that is not
tested at the boundary is a limit nobody knows.

| Name | Value | Note |
|---|---|---|
| `AUTO_ACCEPT_MAX_BYTES` | 20 MB | above this a saved contact still needs a tap |
| `MAX_TRANSFER_BYTES` | 2 GB | was 5 GB |
| `MAX_APK_BYTES` | 500 MB | existing `P2PAppUpdateManager` cap, unchanged |
| `MAX_CONCURRENT_PER_PEER` | 2 | per-peer, not the global semaphore |
| `RATE_MAX_REQUESTS` | 20 | per peer, per window |
| `RATE_WINDOW_MS` | 10 min | |
| `RATE_MAX_AUTOBYTES` | 200 MB | auto-accepted transfers only |
| `PENDING_HOLD_MS` | 5 min | then auto-decline |
| `PENDING_PER_PEER` | 2 | newer is dropped beyond this |
| `PENDING_TOTAL` | 5 | newer is dropped beyond this |
| `FREE_SPACE_MARGIN_BYTES` | 64 MB | added to the declared size |
| `ADMISSION_POOL_SLOTS` | 8 | must exceed `PENDING_TOTAL` |
| `SENDER_OFFER_TIMEOUT_MS` | 6 min | strictly greater than `PENDING_HOLD_MS` |

Rate-limit numbers were proposed with rationale and approved by the user, not
chosen unilaterally: a real burst (a folder of 20 photos plus voice notes) is
roughly 40 to 60 MB, well inside 200 MB, so an ordinary user never meets the
limit. The acknowledged trade-off is a party where one person pushes 30 videos
to 5 people and hits the wall mid-session.

## 3. The signed offer

The admission decision must not key on an unauthenticated sender id, so the
offer is the authenticated root, in the same shape as the 1.8 group
invitation.

`FILE_OFFER` is a signed per-recipient message. Its digest preimage begins
with the fixed label `"LanChat-file-offer-v1"`, then the canonical JSON of:
`senderId`, `recipientId`, `transferId`, `name`, `size`, `kind`, `groupId`,
and `fileSha256`. Signed with the sender's identity key, verified against the
**pinned** key before any field is believed. Lengths are checked before
parsing, as the invitation codec does.

- `transferId` is single-use. A replayed offer cannot admit a second stream.
- The stream that follows must present the same `transferId` and
  `fileSha256`; both are re-checked before the first byte is written.
- The sender computes `fileSha256` in one streaming pass before opening the
  socket. That pass doubles as a pre-send integrity check, and its cost on a
  2 GB file is a named open question in section 11.
- The receiver hashes while writing and compares at the end. A mismatch
  deletes the file and marks the message `FAILED`.

## 4. The decision

`TransferAdmissionPolicy.decide(request)` is a pure function. No Android
imports, no sockets, no disk, no database. Its input is a value carrying peer
device id and ip, the resolved contact state, the verified offer, the declared
size, the kind, the target, the current per-peer counters and the free space
read. Its output is one of:

- `Refused(reason)` - nothing written, no progress row, no message row, no
  receipt.
- `NeedsConsent` - nothing written; a pending item the UI can render.
- `Accepted(limits)` - the existing path, with the caps from section 2.

`RefusedReason` is a closed enum, so the refusal path is testable and each
refusal logs its own reason rather than a generic "rejected":
`NOT_A_CONTACT`, `KEY_CHANGED`, `WRONG_TARGET`, `TOO_LARGE`, `NO_FREE_SPACE`,
`RATE_LIMITED`, `CONCURRENCY_LIMIT`, `UNVERIFIED_OFFER`, `OFFER_EXPIRED`,
`OFFER_REPLAY`, `NOT_A_GROUP_MEMBER`.

### Evaluation order

First match wins, so the log names the first thing wrong, not the last.

1. The offer signature must verify against the pinned key. Failure is
   `UNVERIFIED_OFFER`. There is no "accept anyway" path.
2. The offer must be unexpired and unused: else `OFFER_EXPIRED`, `OFFER_REPLAY`.
3. The target must be me, or a group I am a current member of. The meta's
   `recipientId` is parsed today (`:410`) and never validated; it now is.
4. The peer must be a saved contact: else `NOT_A_CONTACT`. Strangers are
   refused outright, with no prompt.
5. `hasKeyChanged` is refused outright, with no prompt: `KEY_CHANGED`.
6. An APK from a peer that passes 4 and 5 still needs a tap; there is no
   auto-accept path for an executable.
7. `size > MAX_TRANSFER_BYTES` is `TOO_LARGE`. `MAX_APK_BYTES` applies to
   kinds of APK.
8. Free space below `size + FREE_SPACE_MARGIN_BYTES` is `NO_FREE_SPACE`, and
   the refusal records the shortfall.
9. Concurrent incoming transfers from this peer at `MAX_CONCURRENT_PER_PEER`
   is `CONCURRENCY_LIMIT`. This is per-peer; the existing global 25-connection
   semaphore stays as the outer bound.
10. Pending items at `PENDING_PER_PEER` or `PENDING_TOTAL` drops the newest.
11. The rate limiter refuses with `RATE_LIMITED`. It counts against
    `RATE_MAX_REQUESTS` offers and `RATE_MAX_AUTOBYTES` of payload per
    `RATE_WINDOW_MS`, keyed on `(peerId, ip)` so a peer cannot evade it by
    changing address. The byte budget applies to **auto-accepted** transfers
    only: a transfer the user explicitly approved is bounded by free space and
    `MAX_TRANSFER_BYTES` instead, because refusing a file the user just
    approved is the wrong failure. Refusals still consume a request from the
    budget, otherwise a peer could burn the limit for free by offering files
    it was always going to be refused.
12. Otherwise, if the peer is a contact, not key-changed, the kind is not APK,
    and `size <= AUTO_ACCEPT_MAX_BYTES`, the result is `Accepted`.
13. Otherwise `NeedsConsent`.

## 5. Type-level enforcement

There is no seam object and no counter. `AdmittedTransfer` has a constructor
that is internal to the policy module, so the only way to obtain one is to
pass the gate. Every function that writes bytes takes an `AdmittedTransfer`.
The compiler, not a test, is what proves the four receive paths go through
the policy.

## 6. Receive flow, TCP

Header-first means consent costs zero bytes, which is the property that makes
this worth doing.

1. Parse the bounded meta. No disk I/O has happened yet.
2. Verify the offer, re-check `transferId` and `fileSha256`.
3. Ask the policy.
4. `Refused`: close the socket, delete any temp file, log the named reason.
5. `NeedsConsent`: hand off to the admission pool and **suspend** on a
   `CompletableDeferred`. A parked transfer must not hold one of the 25
   connection semaphore slots, and must not block a thread. The pool is
   bounded at `ADMISSION_POOL_SLOTS = 8`, sized above `PENDING_TOTAL` so
   parked transfers cannot deadlock against their own cap.
6. `Accepted`, or consent granted: read and hash to a temp file, compare at
   the end, then rename and insert.

A hold that reaches `PENDING_HOLD_MS` auto-declines and the sender is told.
If a pending item is dropped by the caps, the sender is told that too, rather
than being left waiting.

## 7. Receive flow, mesh

`[unverified]` The intent is to reject at `onPayloadReceived` by cancelling
the payload before any bytes land, using the Nearby Connections incoming
payload cancellation API. **This must be confirmed against the official
Nearby documentation before implementation.** If cancellation cannot precede
the write, mesh consent degrades to holding or discarding bytes that have
already been materialised in a Nearby temp file, and the implementation must
say so rather than promise a guarantee it cannot keep. The admission rules,
the offer, and the consent UX are identical either way.

This also closes a real inconsistency: mesh inline photo and voice write raw
bytes with no at-rest encryption today (`NearbyMeshManager.kt:818-859`), where
the TCP path encrypts at rest. Bringing mesh in line is part of closing the
gate, and the spec will state per-transport at-rest behaviour explicitly
rather than leaving the two paths to drift.

## 8. Consent UX

The tap has to be reachable whether or not you are looking at the app, because
a large file arrives while you are mid-conversation.

- `PendingTransferStore` is in-memory only: a map of `transferId` to peer,
  offer, size, kind and the `CompletableDeferred`. Exposed as a `StateFlow`.
- Home shows a queue row with sender name, kind, size, and accept/decline.
- The relevant chat shows the same item as a dialog, driven by the same
  state, so the two surfaces cannot disagree.
- A notification carries accept and decline actions, which is the only path
  that works when the app is not in the foreground.

### No new table

There is no `pending_transfers` table and no migration 14 to 15. The holds
live in memory as a deferred plus a socket; there is nothing to query after a
restart that would not be better served by re-asking the user, and surviving
a process death mid-consent is not worth a schema change. The sender simply
times out and reports it.

Instead: startup cleanup of orphan `temp_*` files across the four transfer
directories. Those accumulate today from crashes and cancels and are never
swept. Worth having on its own merits.

## 9. Sender side

- `awaitingRecipient` is a real state in the existing progress card, with the
  string "waiting for recipient".
- The sender waits `SENDER_OFFER_TIMEOUT_MS = 6 min`, strictly longer than
  `PENDING_HOLD_MS = 5 min`, so the sender is still alive when consent
  arrives.
- A signed refusal from the receiver moves the row to `FAILED` with the reason
  instead of leaving it hanging.
- Cancel is authenticated: signed over `(transferId, senderId)`, and the
  receiver refuses an unsigned or wrong-sender cancel. Today any peer that can
  reach the JSON port can cancel anyone's `transferId`
  (`TcpMessagingManager.kt:875`).

## 10. No silent fallbacks

Per `AGENTS.md`. Each of these is a test, not a log line.

- Hash mismatch: delete the file, mark the message `FAILED`. Never display it.
- Signature failure: write nothing. There is no "accept anyway".
- Missing pairwise key: refuse. Never downgrade.
- Short free space: refuse and record the shortfall.
- Group target where I am not a current member: refuse.

## 11. Testing

**Layer 1, the rule table.** `TransferAdmissionPolicyTest`, plain JVM, no
Robolectric: every row of section 4 as a table case, plus the constants at
limit-1, limit, limit+1. This is the main evidence.

**Layer 2, the paths.** Per transport: refuses stranger, refuses
`KEY_CHANGED`, refuses oversized, refuses on space, refuses when rate limited,
writes nothing and creates no message row in each case. Consent writes nothing
until accepted. Hash mismatch deletes and fails. Legacy at-rest behaviour per
transport is asserted, not assumed.

**Layer 3, the offer.** `SignedFileOfferRoundTripTest`, modelled on
`SignedMessageRoundTripTest`, because that test exists precisely because the
send and receive halves of a 1.3 protocol once disagreed while everything still
compiled and every message was refused at runtime.

**Layer 4, the flow.** `FileConsentFlowTest`: offer arrives, nothing is
written, accept writes exactly one message row, decline writes none and the
sender is told, expiry declines and the sender is told.

### Open questions, to be measured rather than assumed

- The pre-send hashing cost for a 2 GB file on a phone.
- Whether holding sockets outside the 25-slot semaphore changes the
  connection-admission maths under a 25-peer fan-out.
- Whether the `ADMISSION_POOL_SLOTS = 8` figure is right, or whether the
  admission pool should be unbounded given that a hold is a suspension rather
  than a thread.

## 12. Known gaps this phase does not close

- Group media senders still have no per-peer consent on the send side; the
  gate is inbound only.
- `sendMembershipUpdate` and `sendGroupInviteMessage` still hardcode
  `Dispatchers.IO` (logged as a 1.8 follow-up, unrelated to this phase).
- At-rest encryption on the mesh inline photo and voice paths is aligned to
  TCP as part of section 7, but the mesh FILE path keeps Nearby's temporary
  storage semantics.
- The APK is bound by digest and by Android signing certificate, and the
  offer is signed. It is still not a verified signature over the APK from a
  known publisher identity, which is 1.10's job.
